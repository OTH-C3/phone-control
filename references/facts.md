# 技术事实速查

**这一节只放「跨机器不变、换场景仍成立」的硬结论。** 判据与上序 `GROWTH.md` 的 L1/L2 分层一致：
换一台手机、换一个 App、换一个 agent 之后这些话还对的，才配进来。

坐标、分辨率、某个 App 特有的按钮文案**不在**这里——那些属于 `app-profiles/`。

正文里的 `§2.1` 这种引用指 `SKILL.md` 的章节号，读之前先看 `SKILL.md`。

## dump 与通道

### F1 · `uiautomator dump` 必须落盘再 pull，`exec-out` 拿不到 stdout
`adb exec-out uiautomator dump` 照样往 `/sdcard` 写文件，且**忽略传入的路径**，stdout 只有一句
"UI hierchary dumped to: ..."。要内容就必须先 `adb shell uiautomator dump <手机路径>`，再 `adb pull`。
→ 直连 stdout 的人会拿到一句"成功"却什么都读不到。见 `SKILL.md` §2.1。

### F2 · 手机上没有 `/tmp` 可写，别把 dump 目标写成 `/tmp/x.xml`
那个 `/tmp` 是**手机上**的 `/tmp`，通常不可写，dump 直接失败。
→ 用 `/data/local/tmp/`（默认）或 `/sdcard/`，对应 `config.env` 的 `DUMP_DIR`。

### F3 · dump 打印 "dumped to" 不等于文件真的写进去了
目录不可写、目录不存在时，`uiautomator dump` 照样回这句成功提示，之后 `adb pull` 拉回空。
→ `probe.py` 因此拉完还要判一次文件是否存在且非空，拿不到就报"多半是 DUMP_DIR 不对或不可写"。
**不要只信退出码和那句提示。**

### F4 · dump 导出的是**当前焦点层**，不是目标 App 的窗口
焦点被系统层/通知栏/弹窗抢走时，dump 返回一堆 `text` 为空的容器节点，一条内容都读不到。
这种"读不到"不是"这 App 没内容"，是焦点不在。
→ 每次读内容前先 `dumpsys window | grep mCurrentFocus`（见 F5）。

### F4b · 但 `mCurrentFocus=NotificationShade` **不能当"屏灭了"的判据**（这条我踩过）
`NotificationShade` 是熄屏/锁屏时的**默认焦点层**，但**亮屏时也照样显示它**。
实测：亮屏状态点进微信搜索框，焦点仍是 `NotificationShade`，而操作完全正常
（输入框 `focused=true`、dump 40~110 个节点）。
反过来，屏真灭了时焦点也是 `NotificationShade`。
**同一个现象两种成因，只看焦点会判断错。** 判屏灭与否要看 F28 的 `mWakefulness`。

### F5 · 确认焦点用 `dumpsys window`，不要用 `dumpsys activity activities`
`dumpsys window` 里 `mCurrentFocus` 几行就够。`dumpsys activity activities` 是另一回事（输出 1300+ 行），
用错了是白烧一轮 token。
坑：`topResumedActivity=` 这行**包含 "ResumedActivity" 但没有冒号**，直接 `split(":")` 会越界。

### F6 · dump 结果 8~42KB，必须压缩后进上下文
实测 42KB 界面树压到约 2.5KB（**5.9%**）；第二个 App 的 28321 字节 → 54 条元素，主通道一次读通。
→ 整份读进去是浪费上下文，也让"读到了什么"变模糊。

### F7 · 并发 dump 必须给文件名加唯一后缀
两个任务 dump 到同名文件（最常见的就是 `/sdcard/ui.xml`）会**互相覆盖**，拉回来的是对方那一刻的界面。
→ 时间戳 + 随机串。`probe.py` 已内置（`dev_dump_path()`）。

### F8 · 落盘文件必须用 adb 删，不能用 `os.remove()`
`dev_path` 是**手机上**的路径，本地文件系统里没有这份文件，`os.remove()` 只会抛 `OSError` 被吞掉。
→ 老版本漏在这上面，实测在设备上攒到 106 个 `probe_*.xml`。正确写法：
`adb shell rm -f <手机路径>`，且只删自己那一个。

### F9 · dump 失败/成功都要清掉落盘文件
失败路径尤其容易漏——dump 可能已经写了一部分在那儿。不清就在设备上越攒越多，
而且下次并发时这个文件会被别人拉走，读成错误时刻的界面。

## 操作

### F10 · 顶部和底部都吞点击
状态栏 + 标题栏 + 吸底按钮区域（1080x2400 上是 y≈200，约 **8% 高度**）里，`input tap` 过去没反应。
→ 点不动就换 y 值试它下方的可点区域，**别对着同一坐标反复点**——那只会静默重放。

### F11 · 坐标一律取当前 `probe.py` 输出，不沿用旧值
分辨率不同坐标全漂（同一按钮在 1080x2400 与 1440x3200 上差一大截）。
→ 别的设备、旧记录、上次跑的数值都不能直接抄。

### F12 · `input tap` 参数不全会报 `IllegalArgumentException`
`Argument expected after "tap"` 意味着坐标没传进去，一般是界面已经变了、上一步读到的元素已不存在。
→ 重新 probe 再点，别猜。

### F13 · `input text` 走输入子系统，绕得开输入法
不用等焦点给输入法、不用管软键盘弹没弹。
→ 多输入框串联可以点输入法右下角「下一步」键（`input keyevent` 序列）。
→ **但只支持 ASCII**：中文一个字都发不出去，必须走 F27。

## 滚动读长内容（`scroll_read.py`）

### F14 · 滚动后 dump 里会混进**上一层列表的残留元素**，bounds 是错的
列表（RecyclerView 之类）滚动后，dump 会带回一批已经滚出屏幕的元素残影，
它们的 bounds 是**颠倒**的，例如 `[210,380][746,4]`（y1=4 居然比 y0=380 小）。
实测：屏幕明明已经滚到 Storage/Battery，dump 里还挂着上一屏的
Dark theme/Wallpaper，且 bounds 就是这样颠倒的。
→ 判据：`y1 <= y0`，或整体超出屏幕高度，一律**丢弃**。留着会把读过的内容再混进来。
→ **读取通道和点击通道都要过滤**：`scroll_read.py` 的 `visible_lines()` 已过滤；
`probe.py` 也已在 `parse_ui_full()` 里过滤，并打印丢弃了几条（见 F24）。

### F15 · 滑动后有惯性动画，不能"一变就读"
只在"看到变化"的瞬间读，拿到的是**滚动中间态**：元素位置错乱、部分元素还在屏幕外，
拼接时会多出重复段。
→ 必须**连续两次快照完全一致**才算稳定，然后再取一屏。`scroll_read.py` 的
`read_settled()` 就是这么做的，`--settle` 控制最长等待（默认 1.5s）。

### F16 · 吸顶/吸底元素每屏都在，会造成每屏重复一遍
搜索栏、底部标签栏这类元素位置不动、内容不变，每屏都存在。
→ 拼接前先剥掉"与上一屏**位置相同**的首尾行"。只剥首尾，不碰中间的重复——
聊天里两条一模一样的消息（"哈哈哈"）是合法的，不能误删。

### F17 · "到头了"要按"滑动后界面不再变化"判，不能按"剥完空了"判
滚到最后一屏时，整屏内容和上一屏一样，剥掉吸顶后会只剩吸顶栏。
若用"剥完为空"当到底条件，会在**正常的中间屏**（恰好和上一屏高度重合）上误判提前结束。
→ 顺序必须是：**先判"界面有没有动"，再剥吸顶**。动了才继续，没动才是到底。

### F18 · 连续滑动之间优先用"等界面稳定"，不要固定 sleep
固定 sleep 要么白等（快设备），要么在第 2 屏还没落定时读到中间态（慢设备/动画长）。
→ 与 §3 同一纪律：轮询到稳定为止。

### F19 · 反向读（`--dir up`）时，新内容要**插到前面**，不能往后面接
`--dir up` 用来读更早/更上面的内容（读聊天记录历史就是这条）。它和 down 一样
"一屏屏读进来"，但拼接方向相反：
- down：新内容在已读内容**之后** → 比对「已读尾部 == 新屏头部」，接在后面。
- up：新内容在已读内容**之前** → 比对「已读头部 == 新屏尾部」，**插在前面**。
→ 接错方向，读出来的顺序就是乱的。实测校验法：对同一份列表，down 与 up 读出的
结果应当**逐行相同**（已验证一致）。

### F20 · 吸顶/吸底要按"所有屏的公共前后缀"来找，不能只用相邻两屏
只用相邻两屏比对时，**第一屏没有上一屏可比**，它的吸顶栏会被当成内容收进去，
后续拼接就对齐不上、出现重复段（实测 up 方向就这样重复了 Search Settings 和
Storage 两行）。
→ 改成两遍法：先把所有屏收集起来，取「所有屏都相同的顶部前缀 / 底部后缀」当吸顶吸底，
剥掉之后再拼接。条件更强，既捞出吸顶又不会误伤真实内容。

### F24 · 残留元素的坐标会让点击**点到别的条目**，不只是读重复
F14 说的是残留元素污染**读取**。同样的残留会污染**点击**：残留行的 bounds 是颠倒的，
算出来的"中心点"落在**上一屏**那个位置，照它 `tap` 过去点的是**完全不相干的东西**。
实测：在设置主页滚动后 probe，输出里混进一条
`Battery @ (294,2317) [210,2360][378,2274]`（y0=2360 > y1=2274）；按这个坐标点击，
**跳进了另一个 App**（不是设置里的任何页面）。
→ 教训：**滚动过的页面上，probe 输出不能整份照抄坐标**。`probe.py` 现在会丢弃
bounds 非法的行并打印「丢弃了 N 条残留元素」；要稳妥就先把列表**滑回顶部再 probe**，
顶部一屏没有残留。这也是 F11「坐标取当前 probe 输出」之外的另一道闸。

## 各类界面到底读不读得到（实测，别再凭印象）

**结论先说**：`uiautomator dump` **能读绝大多数 App 的文字**。原生控件自不必说，
**WebView 网页正文也读得到**（读的是渲染后的文字，不是 DOM）。真正读不到的只有
**本就没有文字节点的画面**（画布 / 游戏 / 视频帧 / 纯图片列表）。

### F25 · WebView 页面读得到正文，但必须**等页面加载完**，读太早就只回外壳
- **现象**：打开一个 WebView 页面后**立刻**读，只回几条工具栏/地址栏/按钮元素，
  正文一条都没有，看起来像"这个 App 读不到"。
- **原因**：WebView 渲染后的文字要**页面加载完成**才进无障碍树。
  实测某 WebView 测试页（1080x2400）：
  | 时刻 | 元素数 | 正文命中 |
  |---|---|---|
  | +2.8s | 4 | 0（**只有外壳**） |
  | +5.1s | 13 | 2（`Example Domain` + 正文段落） |
- **做法**：读到"**只有外壳元素**（标题栏 / 地址栏 / 按钮，没有任何正文）"时，
  **不要下"读不到"的结论** —— 等 1~2 秒再读一次，或轮询到元素数稳定（`wait_ui.py` 的思路）。
- **真正的盲区**：画布 / OpenGL / 游戏 / 视频帧 / 纯图片列表，这些**本来就没有文字节点**，
  不是"读早了"，是压根没有。这一类才需要走 §2.4 截图视觉兜底。

### F26 · 权限弹窗和系统弹窗会抢焦点，把当前页的读取顶掉
- **现象**：装了新 App 首次打开，读到的是 `Allow ... to send you notifications?`
  或 `DeprecatedTargetSdkVersionDialog` 这类系统弹窗，目标 App 的内容一条没有。
- **原因**：与 F4 同源 —— dump 读的是**当前焦点层**，弹窗抢走焦点就只读弹窗。
- **做法**：读之前先确认焦点是不是目标包名（§2.0）。遇到系统弹窗，**从 dump 里取按钮
  真实坐标**去点掉（`ALLOW` / `OK` / `DON'T ALLOW` 都在 dump 里有坐标），别按估算坐标点。
  注意：系统弹窗本身**是能读的**（实测 `Messaging` + 整段说明 + `OK` 全读到）。

## 输入文字（中文是硬骨头）

### F28 · 起手先查屏幕状态：屏灭时 `input` 事件被**静默吞掉**（不报错、也毫无反应）
- **现象**：手机熄屏时 `input tap` / `input keyevent` **全部无效，而且不报错** ——
  命令照常 return 成功，界面纹丝不动。实测熄屏下发 `keyevent 4`（返回），
  按键前后 `mCurrentFocus` 完全一致（状态毫无变化 = 事件被吞）。
  此时 dump 只剩约 20 个空壳节点，看起来像"界面读不到"，**极易误判成 F4 的焦点问题**。
- **原因**：Doze 下系统直接吞输入事件。这是系统行为，不是 adb 或本工具的问题。
- **做法（任何操作前先做）**：确认屏幕亮着：

  ```bash
  adb shell dumpsys power | grep mWakefulness     # 要看到 Awake
  ```
  不是 `Awake` 就唤醒：`adb shell input keyevent 26`（电源键）。
  看到 `Awake` 再继续操作。

- **坑一：别反复按电源键**。亮屏时 `keyevent 26` 是**关屏**，于是变成
  "亮一下又熄" —— 用户那边看到的就是手机反复开启又灭掉，很像是手机坏了。
  发一次就等几秒，看 `mWakefulness` 再决定下一步。
- **坑二：锁屏（`isKeyguardShowing=true`）时返回键退不出去是正常行为**，不是 bug。
  手势 / 面部 / 密码解锁只能由人在真机上完成，**别瞎试手势去"破解"**
  （上滑通常是展开通知栏，解不开，还容易误开相机）。
  先把屏幕唤醒，然后把控制权交回给用户，让他自己解锁。
- **坑三**：排查期间别连续跑几十条 adb 命令去"找现象" —— 每发一条都在动用户的手机。

### F27 · `input text` / `input keyevent` **都发不了中文**
- **现象**：`adb shell input text "中文"` 直接报错，中文一个字都进不去：
  `java.lang.NullPointerException: Attempt to get length of null array`。
  改用 `input keyevent <字母键码>` 也不行 —— 输入法只给英文候选，不会出中文。
- **原因**：`input text` 和 `input keyevent` 都是**注入 KeyEvent**，键盘事件表示不了非 ASCII 字符；
  而且注入的事件被系统当作**硬件键盘输入**，中文输入法只当它是英文字母，不走拼音引擎。
  —— 这正是 F13「绕得开输入法」的另一面：**绕得开，也意味着借不到输入法的中文能力**。
- **做法一（推荐）**：用 **yadb** —— **不装 App、不改输入法**。
  **本仓库已自带 `bin/yadb`（不必另外下载；第三方程序，LGPL-3.0，见 `NOTICE.md`）**。
  把 jar `push` 到手机的 `/data/local/tmp`，用 **`app_process`** 直接在手机上跑它。
  它走系统输入管理接口，因此**支持中文**：

  ```bash
  adb push bin/yadb /data/local/tmp/yadb     # 首次一次即可
  adb shell app_process -Djava.class.path=/data/local/tmp/yadb /system/bin \
      com.ysbing.yadb.Main -keyboard "要发的中文"
  adb shell app_process -Djava.class.path=/data/local/tmp/yadb /system/bin \
      com.ysbing.yadb.Main -keyboardClear
  ```
  真机实测（2026-10-02）：`-keyboard` 后输入框 `text` 精确等于注入的中文；`-keyboardClear` 可清空。
  删掉 `bin/yadb` 只影响中文输入，读屏 / 点按 / 滚动读取都不受影响。

  **关键前提：输入框必须先真正聚焦**。没聚焦时它只把文本写进剪贴板（回报类似 `Copy text:true`），
  **并不会进输入框** —— 这是最容易误判成"这工具不行"的地方。
  聚焦的判据：`uiautomator dump` 里那个 `EditText` 的 `focused="true"`。
  先 `input tap` 点进输入框（坐标取 dump 的 bounds 中心），确认 focused 后再注入。
- **做法二（备选）**：装能接收广播文本的第三方输入法，`ime set` 切过去 → `am broadcast` 注入 →
  **用完切回原输入法**（不切回，用户键盘变空壳）。
- **本仓库不附下载地址或镜像**（会失效）：`bin/yadb` 已随仓库分发，来源与许可见 `NOTICE.md`。

### F29 · 输入法键盘是**独立窗口**，dump 读不到它
- **现象**：键盘弹出时 dump 只能拿到应用窗口的元素，**候选词一个都读不到**。
- **原因**：dump 读的是**焦点层**（F4）。输入法属于自己的窗口，与 App 并列，不在 App 的树里。
- **做法**：需要看候选词 / 键盘状态时**走截图**（视觉通道），别指望 dump。
  判断输入法当前是中还是英，也只能靠截图看底部按键。

## 像素兜底

### F21 · `content_rows()` 的阈值保持 0.01
判定"这一行有内容"的像素比例，文字行一般占 2%~15%。
→ 调成 0.5（"半行全黑"）就**永远只命中深色大色块**，文字行全部漏掉。对应 `config.env` 的 `PIXELS_MIN_RATIO`。

## 边界

### F22 · 只支持 Android
iOS 与桌面端不在范围内。

### F23 · 拿不到应用原始数据
需要结构化数据（而非界面）时，先看 `data-layer.md`，大概率不可得，直接回界面层。
界面上读得到的内容（聊天记录、列表、文章）走 dump + 多屏聚合即可，不需要数据层。

### F30 · yadb 各通道的实测差异：只有读屏值得换，截图千万别换
真机实测（2026-10-04，小米 / Android 16）逐条对比 yadb 与原生 adb：

| 用途 | 原生 adb | yadb | 结论 |
|---|---|---|---|
| 读界面树 | `uiautomator dump`+`pull` **2.34~2.45s** | `-layout`+`exec-out cat` **0.47~0.81s** | **换，快 3~5 倍** |
| 截图 | `exec-out screencap` **0.39~0.46s**，12/12 成功 | `-screenshot` 0.54~**5.44s**，**12 次里 5 次卡死** | **别换** |
| 点按 | `input tap` **0.07~0.08s** | `-touch` 0.25~0.41s | 别换，原生更快 |
| 滑动 | `input swipe` 0.27~0.29s | `-swipe` 0.25~0.28s | 持平，按需选 |
| 长按拖拽 | **做不到** | `-longPressDrag` | **只能用 yadb** |
| 双指缩放 | **做不到** | `-pinch` | **只能用 yadb** |

- **读屏数据等价**：同界面 105 节点一一对应，103 个可比节点**属性差异 0 处**。
  yadb 少 `drawing-order` 和 `hint` 两个属性，现有脚本都没用到（已 grep 确认）。
- **`-screenshot` 卡死是设计缺陷**（不是环境问题）：源码 `Screenshot.java` 里
  `acquireLatestImage()` 无新帧时返回 null，`do-while` + `sleep` 重试，
  **硬编码 5 秒超时**才抛异常。屏灭屏亮都一样卡。
  画质与 `screencap` 完全相同（1440x3200、字节数一致）—— **零收益、42% 失败率**。
- **yadb 独有手势签名**（从源码 `Main.java` 确认，勿凭猜）：
  `-longPressDrag <x1> <y1> <x2> <y2> <长按ms> <拖动ms>`、
  `-pinch <中心x> <中心y> <起始距> <结束距> <时长ms>`。
- **两个必须知道的坑**：
  ① **判定成败只能看输出文本，不能看退出码** —— jar 缺失时输出 `Aborted`，
     退出码可能是 0 也可能是 134（取决于有没有被管道截断）。
  ② **跑之前必须先 `rm -f` 输出文件** —— yadb 失败时不会删旧文件，
     不先删就会把上一屏当成这一屏（实测确认）。
  成功信号：`-layout` 看 `layout dumped to:`，`-screenshot` 看 `screenshot success:`，
  `-keyboard` 看 `Copy text:true`。`-swipe` / `-longPressDrag` **无条件**打印自己的名字，
  不能当成功标志。
- `-layout` 和 `-screenshot` 都支持传自定义输出路径（实测有效）。
- `-writeClipboard` **是生效的**（实测写入后 `-readClipboard` 能读回），
  只是它自己**不打印任何确认信息** —— 别因为「没输出」就判定失败。
  但**写空串清不掉剪贴板**（写 `""` 后读回仍是原内容），要清得用 `-keyboardClear`。

### F31 · 读屏已改走 yadb，兜底是 uiautomator（v0.6.0 起）
**现在的实际行为**：`fetch_ui()` 先试 yadb 的 `-layout`，拿不到就自动退回 `uiautomator dump`。
使用者不需要做任何选择，两条通道产出的内容等价。

- **改造后实测（同一屏，亮屏状态）**：yadb 通道 787ms / uiautomator 通道 2288ms，**快 2.9 倍**。
  `probe.py` 整脚本从约 2.3s 降到 0.8s；`wait_ui.py` 等一个已存在的文本从 2 秒级降到 **0.3s**。
- **等价性实测**：46 节点一一对应，42 个 `(class+bounds)` 键全对齐，
  17 个属性里唯一有差异的是 `drawing-order`（yadb 没有，共 46 处），**其余全为 0 差异**。
  → 换通道对解析结果没有任何影响。
- **兜底一致性实测**：把手机上的 jar 挪走，同一条命令输出**元素完全相同**，
  只在「原始 XML 字节数」上差 29 字节（就是少的 `drawing-order`）。
  → 判据是「解析结果一致」，不是「字节一致」。
- **陈旧文件防护要测两种情况**（只测一种会漏掉危险的那种）：
  ① jar 不在 → 前置检查就拦住；
  ② **jar 在但执行失败**（实测：把 jar 换成无效内容，`ls` 查得到、`available=True`，但跑不起来）
  → 这种情况下靠的是调用前那次 `rm -f`。实测确认不会返回上一屏的内容。
- **超时**：yadb 的 layout 与读回各 30 秒，uiautomator 90 秒，yadb 卡住不至于让整个脚本挂死。
- jar 放在手机上的位置可用 `config.env` 的 `YADB_JAR` 改，默认 `/data/local/tmp/yadb`。
  **手机上看不见 jar 时功能完全不受影响**，只是慢一些。
